## 2. 命名规范

### 2.1 目录与文件

| 场景 | 规则 | 示例 |
|---|---|---|
| 业务模块目录 | 单数小写驼峰 | `src/skill/`、`src/scheduledTask/`、`src/taskRun/` |
| 模块内文件 | `{module}.{role}.ts`，role ∈ `entity/dto/repository/service/controller/router` | `skill.controller.ts` |
| 外部连接/单例工具 | 大写驼峰 | `Logger.ts`、`Redis.ts`、`MongoDB.ts`、`Axios.ts` |
| 纯函数工具 | 小写驼峰 | `zip.ts`、`parseXML.ts`、`mailer.ts` |
| 中间件 | 小写驼峰 + `Middleware` 后缀 | `jwtMiddleware.ts`、`responseMiddleware.ts` |
| 常量类 | 大写驼峰 | `HttpStatus.ts`、`CacheConstants.ts` |
| 基础实体 | `base.entity.ts` / `base.mongo.entity.ts` | `utils/entities/` |
| 测试文件 | 对应单元，以 `.test.ts` 结尾 | `jwtMiddleware.test.ts` |

### 2.2 模块六件套命名

| 文件 | 类/导出命名 | 实例导出 |
|---|---|---|
| entity | `interface I{Module}`、`type {Module}Document`、`{Module}Schema`、`{Module}Model` | 默认导出 Model |
| dto | `Create{Module}Dto` / `Update{Module}Dto` / `{Module}QueryDto` / `PaginatedResponse<T>` | type 导出 |
| repository | `class {Module}Repository` | `export const {module}Repository` |
| service | `class {Module}Service` | `export const {module}Service` |
| controller | 具名导出函数（见下） | — |
| router | 默认导出 `router` | `export default router` |

Controller 具名导出函数统一采用：`list{Module}s`、`get{Module}ById`、`create{Module}`、`update{Module}`、`delete{Module}`、`batchDelete{Module}s`。

### 2.3 接口与类型

- 业务实体接口：`I{Module}`，**必须** `extends IBaseMongoEntity`。
- Document 类型：`type {Module}Document = BaseDocument & I{Module}`。
- DTO 统一后缀：`CreateXxxDto` / `UpdateXxxDto` / `XxxQueryDto`。
- 分页响应：`PaginatedResponse<T>`（`{ list, total, page, limit }`）。
- 状态类型：`type {Module}Status = 'active' | 'inactive' | ...`，枚举值一律**小写**。
- 基础类型：`IBaseMongoEntity`、`BaseDocument`、`BaseMongoPlugin`（来自 `utils/entities/base.mongo.entity.ts`）。

### 2.4 命名空间（namespace）

**所有新增类型声明必须统一放在 `type/index.d.ts`，以 namespace 方式声明在对应的 namespace 中，再导入使用；严禁在各自的文件中声明类型。**

```ts
// type/index.d.ts
export namespace User {
  interface Profile {
    id: string;
    name: string;
  }
}

// 使用方
import type { User } from '../../type/index.d.ts';
const profile: User.Profile = { id: '1', name: 'x' };
```

namespace 写法：`export namespace Xxx { ... }`，一个业务域一个 namespace。环境变量类型声明除外，仍放 `utils/types/env.d.ts`。

### 2.5 函数与变量

- 函数名动词开头 + 名词：`list` / `get` / `create` / `update` / `delete` / `batchDelete`。
- 变量小写驼峰：分页参数 `page` / `limit`；结果统一 `result`，创建/更新结果 `created` / `updated`，错误用 `error`。
- 判别联合返回值用 `{ created } / { error }` 形态，避免布尔/字符串传值判断。

### 2.6 常量与枚举

- 常量类：`public static readonly XXX: number = 200;`（见 `HttpStatus`）。
- 业务 Redis key：统一收敛到 `CacheConstants`，如 `wxbot:access_token:`。
- 状态/类型枚举值：小写字符串（`'active'`），Schema 中用 `enum: [...] as XxxStatus[]` 约束。

### 2.7 配置与路由路径

- 环境变量：大写蛇形，如 `DB_HOST`、`MONGO_URL`、`JWT_ENABLED`；由 `utils/env.ts` 在启动时加载进 `process.env`，业务代码直接读 `process.env.X`（带默认值），类型声明在 `utils/types/env.d.ts`。
- 路由路径：`/api/{module}s`（复数、小写）；唯一标识类 key 用小写连字符（`^[a-z0-9]+(?:-[a-z0-9]+)*$`，如 Skill key）。
- 业务提示信息：统一中文，如 `'Skill 创建成功'`、`'xxx 不存在'`。

## 3. 架构与分层

### 3.1 模块六件套

每个业务模块在 `src/{module}/` 下由 6 个文件组成：

```
{module}.controller.ts   # 路由处理：解析 req → 组装 DTO → 校验 → 调 service → 响应
{module}.service.ts      # 业务逻辑：跨仓储编排、级联、事务；返回判别联合
{module}.repository.ts   # 数据库访问：所有 Mongo/TypeORM 查询只出现在这里
{module}.dto.ts          # 入参 / 查询 / 分页类型
{module}.entity.ts       # Schema + Model（Mongo）或 TypeORM 实体（MySQL）
{module}.router.ts       # express.Router()，声明路由与中间件，默认导出
```

新增模块后必须到 `src/index.ts` 用 `router.use('/{module}s', {module}Router)` 注册。

### 3.2 职责边界（强约束）

| 层 | 允许做的事 | 严禁 |
|---|---|---|
| controller | 解析参数、组装 DTO、参数校验、调用 service、`res.sendSuccess/sendFail` | 写业务逻辑、直接查库 |
| service | 业务编排、跨仓储组合、级联副作用、返回 `{ data } / { error }` 判别联合 | 直接操作请求/响应对象 |
| repository | 唯一的数据库访问点，封装查询、分页、原子更新 | 写业务逻辑 |
| router | 声明路由与上传中间件 | 内联业务代码 |

service 与 repository 中依赖注入统一用**实例单例**：`import { {module}Service } from './{module}.service.ts'`，不 new、不传参构造。

### 3.3 依赖方向

```
router → controller → service → repository → entity / Model
```

- 跨模块：允许 service 层 import 其他模块的 repository / service（如 `subscription.service` 依赖 `skill.repository`）。
- **禁止** controller 直接 import 其他模块的 repository。
- 基础工具（`utils/`）可被任意业务模块依赖；业务模块禁止反向依赖。

### 3.4 单例服务

所有外部连接服务（Redis、MongoDB、Axios、Logger）均为单例：

```ts
class XxxService {
  private static instance: XxxService;
  public static getInstance(): XxxService { ... }
}
```

新服务继承/参考 `utils/Singleton.ts`。业务侧统一通过 `getInstance()` 或模块导出的 `{module}Service` 单例访问。

### 3.5 中间件链

```
cors → express.json → urlencoded → bodyParser.text(xml)
→ RequestLogger → responseMiddleware
→ /api/* → jwtMiddleware → operationLogMiddleware → 业务 router
→ ErrorLogger
```

- 路由统一挂 `/api` 前缀；JWT 与操作日志由中间件统一处理，业务路由无需重复实现鉴权。
- 新增全局逻辑优先考虑中间件，而非散落到各 controller。

## 4. 数据库与仓储

### 4.1 MongoDB 实体规范（强约束）

参考 `src/skill/skill.entity.ts`、`src/scheduledTask/scheduledTask.entity.ts`：

1. **必须继承基础实体**：`interface I{Module} extends IBaseMongoEntity`，并通过 `Schema.plugin(BaseMongoPlugin)` 注入 `createBy / updateBy / remark / flag / params`。
2. Schema 选项必须包含 `{ timestamps: true, collection: '{module}s' }`（collection 复数小写）。
3. Document 类型：`type {Module}Document = BaseDocument & I{Module}`。
4. Model 单例：`MongoDBService.getInstance().getMongoose().model('{Module}', {Module}Schema)`。
5. 字段约束：
   - `required: true` 的字段**不要**给 default。
   - 需要筛选/排序的字段加 `index: true`（如 `userId`、`status`、`key`）。
   - 唯一字段加 `unique: true` 并配 `trim` / `match` 校验。
   - 状态字段用 `enum: ['active', 'inactive'] as XxxStatus[]`。
   - 灵活结构用 `mongoose.Schema.Types.Mixed`，默认 `{}`。
6. `createBy / updateBy / remark / flag / params` 等基础字段统一由 Plugin 提供，**不得**在业务 Schema 中重复定义。
7. **`flag` 语义与删除约束**：`flag` 由 `BaseMongoPlugin` 注入（`{ type: Number, default: 1, select: false }`），`1` = 未删除、`0` = 已删除。删除一律假删除（flag 置 `0`），严禁 `findByIdAndDelete / findOneAndDelete / deleteMany` 物理删除；所有查询（含分页 list 的 `find` 与 `countDocuments`）必须显式过滤 `flag: 1`，只返回未删除数据。详见 §4.4。

### 4.2 MySQL / TypeORM 实体规范

- 实体类继承 TypeORM `BaseEntity`（参考 `src/siteMenu.ts`）。
- TypeORM 自动扫描 `src/**/*.entity.ts`（`utils/mysql.ts` 初始化）。

### 4.3 Repository 规范

- **分页查询**：`page`/`limit` 分别 clamp 到 `[1, +∞)` 与 `[1, 100]`；用 `Promise.all([find().sort().skip().limit().lean(), countDocuments()])`，返回 `PaginatedResponse`。
- **关键字搜索**：先 `escapeRegex`（`keyword.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')`），再用 `$regex + $options: 'i'` 组合 `$or`。
- **更新**：`findOneAndUpdate`，必须带 `{ new: true, runValidators: true }`。
- **删除：一律假删除**：`updateOne / updateMany({ <筛选>, flag: 1 }, { flag: 0 })`，单条返回 `boolean`、批量返回 `modifiedCount`，严禁物理删除（详见 §4.4）。
- **唯一性判断**：`Model.exists({ ... })`，返回 `boolean`，避免 findOne 后判空。
- **原子计数**：用 `$inc`；需要下限保护时加条件，如 `{ key, downloadCount: { $gt: 0 } }`。
- **批量查询**：`Model.find({ key: { $in: keys } })`。
- 默认排序：`sort({ createdAt: -1 })`。
- Repository 方法按操作命名：`findMany / findById / findByKey / existsByXxx / create / updateByXxx / softDeleteByXxx / incrementXxx / cancelAllForXxx`（删除方法统一 `softDeleteByXxx`，假删除）。
- **查询过滤（强约束）**：所有查询方法必须显式带 `flag: 1`（分页 `find`、`countDocuments`、`findById`、`findByXxx`、`existsByXxx`、批量 `findByIds` / `findByKeys` 统一加），保证只返回未删除数据。

### 4.4 假删除（软删除）规范（强约束）

- **`flag` 语义**：`1` = 未删除 / `0` = 已删除。由 `BaseMongoPlugin` 注入（`{ type: Number, default: 1, select: false }`），不参与查询返回但可作为过滤条件。
- **删除必须假删除**：删除接口只把目标记录 `flag` 置 `0`，不物理删除；严禁 `findByIdAndDelete / findOneAndDelete / deleteMany`。例外：订阅模块 `cancel()` 内清理 `status: 'cancelled'` 的 `deleteMany` 属唯一索引数据卫生特例，保留。
- **方法命名**：`softDeleteByXxx(id/key)` / `softDeleteByIds(ids)`。
  - 单条：`updateOne({ <唯一键>, flag: 1 }, { flag: 0 })`，返回 `boolean`（`modifiedCount > 0`）。
  - 批量：`updateMany({ <筛选>, flag: 1 }, { flag: 0 })`，返回 `modifiedCount`。
- **查询过滤**：所有查询方法显式带 `flag: 1`（分页 `find` + `countDocuments` 都带），只返回未删除数据。
- **唯一键恢复**：唯一字段（如 Skill `key`）被假删除后记录仍在；重新创建同 key 时 `existsByKey`（flag:1）为 false，但直接 `create` 会触发 11000 重复键错误。创建前先尝试恢复 `flag:0` 记录（`findOneAndUpdate({ key, flag: 0 }, { $set: { ...dto, flag: 1 } }, { new: true })`），恢复不到再 `create`（参考 `skill.service.ts` `create`）。
- **文件模块特例**：假删除仅置位 DB 记录 `flag:0`，磁盘文件保留（不 `fs.unlink`），避免破坏仍被引用/分享的下载资源。
- **参考实现**：`wx/material/wxMaterial.repository.ts` `softDeleteByMediaId`。

## 5. TypeScript 规则

1. **新增类型声明统一收敛到 `type/index.d.ts`（namespace 方式），严禁在各自文件中声明类型**（见 §2.4）。
2. `strict` 全开，`noUncheckedIndexedAccess: true`：索引/解构访问必须处理 `undefined`。
3. `verbatimModuleSyntax: true`：类型导入必须 `import type { ... }`。
4. 相对导入一律带 `.ts` 后缀（ESM + tsx）。
5. 路径别名 `@/*` → `src/*`。
6. 环境变量类型声明在 `utils/types/env.d.ts`。
7. 配置直接读 `process.env.X`（类型声明见 `utils/types/env.d.ts`）；`.env` 由 `utils/env.ts` 在启动时加载，业务代码不要自行 `dotenv.config`。

## 6. 响应与错误处理

- 统一 `ResultVO<T>`：`{ code, msg, data, timestamp }`（`utils/types/global.d.ts` 全局声明）。
- 成功：`res.sendSuccess(data, msg?)`；失败：`res.sendFail(msg?, code?)`。
- 错误码统一取 `HttpStatus`（`utils/constant/HttpStatus.ts`），语义规则：

| 场景 | 码 |
|---|---|
| 参数缺失/非法 | `BAD_REQUEST` (400) |
| 未授权 | `UNAUTHORIZED` (401) |
| 资源不存在 | `NOT_FOUND` (404) |
| 业务冲突（重复 key / 已订阅） | `CONFLICT` (409) |
| 系统内部错误 | `ERROR` (500) |

- Controller 统一 try/catch：`const message = err instanceof Error ? err.message : 'xx失败'`，再 `res.sendFail(message, HttpStatus.ERROR)`。
- id 类参数先 `Types.ObjectId.isValid(id)` 校验。

## 7. 文件上传

- 上传中间件在 `utils/middleware/uploadMiddleware.ts`：`uploadSingle`（单文件 `file`）、`uploadMultiple`（`files` ≤10）、`uploadSkillFiles`（`file` + `icon` 双字段）。
- 文件落盘到 `src/file/file.config.ts` 的 `uploadDir`，文件名 UUID 重命名、保留扩展名、按 `Y/M/D` 分子目录；白名单 MIME + `maxFileSize` 限制。
- 业务侧先经 `fileService.upload()` 拿到相对路径，再存入自己的 entity（参考 `skill.controller.ts` 的 `handleUploadedFile`）。
- 删除文件为假删除：仅将文件记录 `flag` 置 `0`，磁盘文件保留（不删除磁盘文件），避免破坏仍被引用的资源。

## 9. 测试规范

## 10. Git 提交规范

- 格式：`<type>: <中文描述>`（冒号全角或半角均可，保持统一）。
- type 取值：`feat`（新功能）、`fix`（修复）、`docs`（文档）、`del`（删除）、`refactor`（重构）、`perf`（性能）、`test`（测试）、`chore`（杂项）。
- 涉及具体模块可加 scope：`feat(skill): xxx`。
- 描述用中文、简洁陈述改动，如 `feat：定时任务新增workspace字段`。

## 11. 其他约定

- 路由注释用 JSDoc 标注 `GET /api/xxx`。
- 业务提示信息统一中文，文案格式：`'{模块} 创建成功'` / `'{xxx} 不存在'` / `'xxx 为必填字段'`。
- 不修改 `main.ts` 启动顺序与 `.env.*` 结构约定；环境变量按 `.env.development` / `.env.production` 分布。
- 本规范由 `.claude/skills/genreal-server/` 或 `.commandcode/skills/genreal-server/` 下的 skill 在 AI 编码时自动引用；人工开发同样以本文为准。
